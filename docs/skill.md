# Comandi del plugin `kit`

Riepilogo delle dieci skill del plugin, che si lanciano digitando `/kit:` seguito dal nome. Tutte le skill, tranne `/kit:pr-develop`, hanno `disable-model-invocation` e non partono mai da sole. Le sei che scrivono o pubblicano (`avvia-progetto`, `buonasera`, `commit-passo`, `pr-main`, `regole` e `pr-develop`, che però può lanciarla Claude dopo il sì dell'utente) sono a lancio manuale, tranne quanto detto. Le letture e i controlli (`buongiorno`, `modelli`, `revisione`, `verifica`) dichiarano `disallowed-tools: Edit Write NotebookEdit` e quindi non possono modificare file (`Bash` resta disponibile: lì vale solo l'hook `guard-commands`). `/kit:pr-develop`, proposta da `/kit:commit-passo` dopo il sì dell'utente, è l'unica che Claude può lanciare da sé; la sua descrizione compare nell'elenco di ogni sessione. Nessun comando ha opzioni con nome (`--flag`): quando c'è, l'argomento è uno solo e facoltativo, e se manca la skill lo chiede o usa il lavoro corrente.

Ogni skill dichiara nel frontmatter il campo `model`: `haiku` per `buongiorno` e `modelli` (procedure brevi e meccaniche); `sonnet` per le altre otto, comprese `avvia-progetto`, `pr-main`, `commit-passo`, `regole` (scrive o sovrascrive file) e `revisione` (analisi per tema). Il modello vale solo per il turno in cui la skill parte: se la skill pone una domanda, dopo la risposta si torna al modello della sessione.

| Comando | Cosa fa | Argomento (facoltativo) |
|---|---|---|
| `/kit:buongiorno` | Riprende il lavoro dalle issue del progetto (issue padre e sue sub-issue, con `gh`; anche una padre ancora aperta con le sub-issue tutte chiuse), riassume dove si è arrivati e propone il primo passo. | Nessuno |
| `/kit:buonasera` | Salva lo stato dei lavori nelle issue (chiude le sub-issue verificate, registra la ripartenza sulla issue padre, apre le issue dei problemi nuovi); aggiorna senza conferma `CHANGELOG.md`, `README.md` e la wiki (se presente), secondo `documentazione.md`; propone di cancellare i file non più utili (solo con conferma) e ricorda `/clear` o `/compact`. | Nessuno |
| `/kit:avvia-progetto` | Avvia un progetto nuovo in un solo percorso: domande di avvio una per messaggio (profilo compreso), copia delle regole (caso A di `regole`) e compilazione del `CLAUDE.md`. | `[nome-progetto]`: nome del progetto |
| `/kit:regole` | Gestisce le regole di un progetto: se non le ha, le copia dal template con i moduli e il profilo scelti (caso A); se le ha già, le confronta con il template e le aggiorna con conferma e `.bak` (caso B); con la sincronizzazione all'avvio attiva, pone una per volta le domande in sospeso (conflitti, moduli nuovi, file fuori posto; caso C). | `[cartella-progetto]`: cartella di destinazione; se manca usa la cartella corrente quando è valida, altrimenti la chiede |
| `/kit:commit-passo` | Crea i commit locali in sequenza e senza conferme intermedie (il lancio è il via libera), mai su `main` o `develop` (crea il branch di lavoro); apre una issue padre con una sub-issue per commit solo con almeno tre commit, fuori da `mini` e se il lavoro non ha già una issue (altrimenti usa quella o tiene il piano in chat). | Nessuno |
| `/kit:pr-develop` | Apre con `gh` la PR dal branch di lavoro (`feature/*`, `bugfix/*`) verso `develop`; richiede la GitHub CLI installata e autenticata. | Nessuno |
| `/kit:pr-main` | Apre con `gh` la PR da `develop` (o `release/*`, `hotfix/*`) verso il branch principale; dopo il merge, con `pulizia` come argomento, verificato con `gh`, pulisce i branch di lavoro le cui PR risultano mergiate e allinea `main` e `develop`; richiede la GitHub CLI installata e autenticata. | `[branch-sorgente]` oppure `pulizia`: con `pulizia` non apre PR ma fa la pulizia dopo il merge; il branch è quello di partenza e, se manca, il branch corrente se è `release/*` o `hotfix/*`, altrimenti `develop` |
| `/kit:verifica` | Controlla il lavoro corrente contro la checklist di consegna del profilo (`qualita.md` §0b; con `mini`, `checklist-mini.md`), poi esegue i controlli di una soluzione .NET (ripristino, formattazione, build senza avvisi, `using` inutilizzati, test, pacchetti vulnerabili, modello EF, compose, spazi bianchi) o di un frontend Angular (`frontend.md`: lint, test, build, audit npm, `any`, colori fissi, traduzioni), o di entrambi, senza modificare file. | `[cartella]`: controlla solo quella (`.sln`, `package.json` con `angular.json`, o entrambi); se manca, i file toccati dal lavoro decidono quali parti controllare |
| `/kit:revisione` | Revisione in sola lettura per tema: `accessi-api`, `dati-efcore`, `gdpr-dati`, `accessibilita-ui`, `colori-tema`, `localizzazione`, `qualita-test`, `review-regole` e `sicurezza` (lancia anche `/security-review`). Senza tema elenca i temi e chiede quale usare. | `<tema>` e, facoltativo, `[cartella-o-percorso]`: ambito da esaminare; se manca usa il lavoro corrente |
| `/kit:modelli` | Mostra quali modelli sono stati usati nella sessione corrente e per cosa (sessione, skill, subagent), leggendo il registro della sessione e non il contesto del modello; sola lettura. | Nessuno |

Dettagli di ogni comando: [README](../README.md) e pagina [Plugin](http://wiki.aepserver.it/claude-config/plugin) della wiki.
