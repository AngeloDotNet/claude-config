# PR verso develop

Rispondi in italiano. Una sola domanda per messaggio e attendi la risposta. Titolo e descrizione della PR in inglese, come i messaggi di commit. Non fare mai `push --force`, non fare il merge della PR e non cancellare branch: il merge (squash) resta all'utente.

0. **Prerequisito: GitHub CLI installata e autenticata.** Prima di tutto, in sola lettura: `gh --version` e `gh auth status`. Se `gh` non è installata o non è autenticata, **termina subito** senza eseguire altro: di' all'utente quale dei due manca e cosa fare (installare la GitHub CLI; `gh auth login` da lanciare lui con `! gh auth login`, perché è interattivo). Questa skill non si usa senza `gh`. Non usare `gh` per altro che questa verifica e l'operazione richiesta.
1. **Branch di partenza.** Esegui `git branch --show-current`. Se è `main`, `develop` o vuoto (detached HEAD), termina: la PR parte da un branch di lavoro. Se il nome inizia con `release/` o `hotfix/`, termina e indica `/kit:pr-main`: queste PR vanno verso il branch principale con merge commit. Se il nome non è `feature/…` o `bugfix/…`, chiedi con una sola domanda se procedere comunque.
2. **Riga nel `CLAUDE.md`.** Leggi nel `CLAUDE.md` della radice la riga «GitHub CLI (gh) installata». Se manca o dice «no» (ora che il passo 0 ha verificato `gh`), chiedi con una sola domanda di confermare che è installata e scrivi la riga `- **GitHub CLI (gh) installata:** sì (AAAA-MM-GG)` nella sezione «Eccezioni alle regole globali»: il hook `guard-commands` blocca `gh pr` senza quella riga.
3. **Stato.** In sola lettura: `git status --short` (se ci sono modifiche non committate, segnalalo e chiedi se procedere comunque: la PR conterrà solo i commit), `git log --oneline origin/develop..HEAD` per i commit della PR e `git diff --stat origin/develop...HEAD`. Se `develop` non esiste in locale o sul remoto, termina e chiedi come procedere. Se non ci sono commit rispetto a `develop`, dillo e termina. Se `develop` è avanzato rispetto al punto di partenza del branch (`git rev-list --count HEAD..origin/develop`), o ci sono conflitti, segnalalo: l'aggiornamento del branch (merge o rebase) resta all'utente.
4. **Controlli di consegna.** Verifica in sola lettura la checklist di `core.md` §0b sul lavoro del branch (build e test, `README.md` e `CHANGELOG.md`, migrazione, test di sicurezza dove pertinenti) e riporta le voci mancanti; non segnarle ok senza averle verificate. Ricorda che la CI deve essere verde prima della review.
5. **Titolo e descrizione.** Proponi:
   - **titolo** in Conventional Commits (`tipo(scope): descrizione`, minuscolo, senza punto, al massimo 72 caratteri): diventa l'oggetto del commit di squash su `develop`;
   - **descrizione** con le sezioni di `git.md` («Pull Request»): cosa cambia e perché, come è stato testato, impatti (migrazioni, variabili d'ambiente, breaking change), `Closes #N` se c'è un'issue, e per la UI screenshot o note su temi e lingue verificati. Chiudi con la riga `🤖 Generated with [Claude Code](https://claude.com/claude-code)` se il `CLAUDE.md` chiede l'attribuzione di Claude.
   Se il tipo del titolo è ambiguo (più tipi nei commit del branch), chiedilo con una sola domanda.
6. **Conferma.** Mostra branch, `develop` come destinazione, titolo, descrizione e comandi che eseguirai, e chiedi con una sola domanda: «Faccio push del branch e apro la PR?». Senza un sì non eseguire nulla.
7. **Esecuzione.** Dopo il sì: `git push -u origin <branch>` (push normale, mai forzato); poi `gh pr create --base develop --head <branch> --title "<titolo>" --body-file <file temporaneo>` con la descrizione in un file nella cartella temporanea della sessione. Se `gh pr create` segnala che la PR esiste già, mostra l'indirizzo e non crearne un'altra. Il hook `guard-commands` blocca `gh pr` finché la riga del passo 2 non dice «sì»: non aggirarlo.
8. **Chiusura.** Mostra l'indirizzo della PR. Ricorda che il merge è con **squash**, a cura dell'utente, e che la CI deve essere verde. Non usare `gh` per altro (né stato, né CI, né altre PR).
