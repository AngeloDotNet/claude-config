# PR verso il branch principale

Rispondi in italiano. Una sola domanda per messaggio e attendi la risposta. Titolo e descrizione in inglese. Non fare mai `push --force`, non fare il merge della PR, non cancellare branch (salvo al passo 10, solo quelli con la PR verificata come mergiata) e non creare tag o rilasci: sono richieste a parte.

**Due modi di lancio.** Senza argomento, o con il nome di un branch sorgente, la skill apre la PR (passi 0-9). Con l'argomento `pulizia` (`/kit:pr-main pulizia`), da usare dopo il merge, non apre nessuna PR: esegui il passo 0, ricava il branch principale come al passo 1 (senza cercare una sorgente), salta i passi 2-9 e vai al passo 10. Lanciare la skill con `pulizia` vale come conferma dell'utente che il merge è avvenuto, da verificare comunque con `gh`. `pulizia` non è mai il nome di un branch sorgente.

0. **Prerequisito: GitHub CLI installata e autenticata.** Prima di tutto, in sola lettura: `gh --version` e `gh auth status`. Se `gh` non è installata o non è autenticata, **termina subito** senza eseguire altro: di' all'utente quale dei due manca e cosa fare (installare la GitHub CLI; `gh auth login` da lanciare lui con `! gh auth login`, perché è interattivo). Questa skill non si usa senza `gh`. Non usare `gh` per altro che questa verifica e l'operazione richiesta (e, in `pr-main`, la lettura dello stato delle PR dei branch di lavoro).
1. **Branch principale e sorgente.** Il branch principale è la voce «Branch principale» del `CLAUDE.md`; se è un segnaposto o manca, usa quello di `git symbolic-ref refs/remotes/origin/HEAD`. Se non è `main`, segnalalo e chiedi con una sola domanda se usarlo così com'è o adottare `main` e `develop` (non rinominare nulla di tua iniziativa). La sorgente è l'argomento, altrimenti il branch corrente se inizia con `release/` o `hotfix/`, altrimenti `develop`. Se `develop` non esiste (sorgente `develop`), termina e chiedi come procedere.
2. **Stato in sola lettura.** Prima `git fetch origin` (aggiorna solo i riferimenti remoti: senza, i confronti con `origin/*` possono essere vecchi e non far emergere un `main` avanti rispetto a `develop`). Poi `git status --short` (modifiche non committate: segnalale, la PR contiene solo i commit), `git log --oneline origin/<principale>..<sorgente>` per i commit che arrivano, `git diff --stat origin/<principale>...<sorgente>`. Se non ci sono commit nuovi, dillo e termina. Verifica che la sorgente sia allineata al remoto (`git rev-list --count <sorgente>..origin/<sorgente>`); se è indietro, segnalalo: l'aggiornamento è dell'utente.
3. **Riga nel `CLAUDE.md`** (dopo lo stato, perché la scrittura sporca l'albero). Leggi nel `CLAUDE.md` della radice la riga «GitHub CLI (gh) installata». Se manca o dice «no» (ora che il passo 0 ha verificato `gh`), chiedi con una sola domanda di confermare che è installata e scrivi la riga `- **GitHub CLI (gh) installata:** sì (AAAA-MM-GG)` nella sezione «Eccezioni alle regole globali»: il hook `guard-commands` blocca `gh pr` senza quella riga.
4. **`main` avanti rispetto a `develop`.** Solo con sorgente `develop` o `release/*`: esegui `git rev-list --count origin/<sorgente>..origin/<principale>`. Se è maggiore di zero (dopo un hotfix, o dopo uno squash già avvenuto), una PR verso il principale andrebbe in conflitto (`add/add`) sui file già portati. Non aprire la PR. Spiega il problema e proponi, con una sola domanda, il branch locale `bugfix/sync-main-into-develop` da `develop` (se esiste già in locale o sul remoto, ad esempio di una sincronizzazione precedente, proponi il primo nome libero `bugfix/sync-main-into-develop-2`, `-3`, ... senza cancellare né riusare quello vecchio; verifica con `git branch --list` e `git ls-remote --heads origin`) con un merge commit di `main` (messaggio `chore(repo): merge main into develop`, con il numero della PR di origine se noto: `merge` non è un tipo di commit ammesso, `git.md`; conflitti risolti a favore di `develop` quando il contenuto di `main` è una versione più vecchia, mostrando le versioni a confronto e il motivo, e applicando la risoluzione solo dopo l'ok). Quella PR verso `develop` va chiusa **con merge commit**, non con squash, altrimenti il conflitto torna: dopo il merge l'utente rilancia questa skill.
5. **Versione e rilascio.** Se la PR porta un rilascio, controlla in sola lettura che il file di versione e la voce `### Rilascio X.Y.Z` del `CHANGELOG.md` siano coerenti con quanto indicato nel `CLAUDE.md`; il commit di bump (`chore(release): bump version to X.Y.Z`) lo prepari solo se l'utente lo chiede. Verifica la checklist di consegna del profilo del progetto (scelta come in `../verifica/SKILL.md`, sezione 0, passo 1) sul lavoro che entra e riporta le voci mancanti.
6. **Titolo e descrizione.** Proponi un titolo Conventional Commits (per esempio `merge: …` o `chore(release): …`, al massimo 72 caratteri) e una descrizione con i commit che entrano raggruppati per categoria (**Aggiunto**, **Modificato**, **Corretto**, **Sicurezza**), gli impatti (migrazioni, variabili d'ambiente, breaking change) e il riferimento alle issue (`Closes #N`). Il commit di merge avrà oggetto `merge: <sintesi> (#NNN)` con un corpo che riassume la funzionalità: dillo all'utente, che fa il merge. Chiudi con `🤖 Generated with [Claude Code](https://claude.com/claude-code)` se il `CLAUDE.md` chiede l'attribuzione di Claude.
7. **Riepilogo.** Mostra sorgente, destinazione, titolo, descrizione e i comandi che stai per eseguire, e procedi senza attendere conferma: lanciare la skill è il via libera dell'utente.
8. **Esecuzione.** `git push -u origin <sorgente>` se la sorgente non è già sul remoto allineata (push normale, mai forzato); poi `gh pr create --base <principale> --head <sorgente> --title "<titolo>" --body-file <file temporaneo>`. Se la PR esiste già, mostra l'indirizzo e non crearne un'altra. Il hook `guard-commands` blocca `gh pr` finché la riga del passo 3 non dice «sì».
9. **Chiusura.** Mostra l'indirizzo della PR. Ricorda: merge con **merge commit**, mai squash né rebase; il lint dei commit non si esegue sulle PR verso il principale; dopo un `hotfix/*` il ritorno di `main` in `develop` è un merge commit. Il merge è a cura dell'utente. Se la PR porta un rilascio, ricorda che il tag `X.Y.Z` (senza `v`, annotato) si crea solo **dopo** il merge su `main`, sul commit di merge (`git-avanzato.md`, «Rilascio»), e che Claude chiede il via dell'utente prima di crearlo e di fare il push del tag, anche senza una sua richiesta; dopo il tag propone anche `gh release` e chiede il via. Questa skill non crea né tag né rilasci. Chiudi dicendo che, fatto il merge, la pulizia dei branch si lancia con `/kit:pr-main pulizia`, anche in una sessione nuova. Usa `gh` solo per questa PR e, al passo 10, per leggere lo stato della PR verso il principale e delle PR dei branch di lavoro.
10. **Dopo il merge: pulizia dei branch e allineamento.** Si esegue con `/kit:pr-main pulizia`, oppure nella stessa sessione quando l'utente dice di aver fatto il merge. Prima individua la **PR sorgente** (sola lettura): se in questa sessione hai aperto tu la PR, è quella; altrimenti è la più recente di `gh pr list --base <principale> --state all --limit 5 --json number,state,headRefName,mergedAt,url`, e in una riga dici quale è (numero, branch, stato). Se non è `MERGED`, o non ce n'è nessuna, dillo e termina senza cancellare né cambiare nulla. Poi Claude verifica con `gh` (sola lettura) lo stato delle PR dei branch di lavoro: `gh pr list --head <branch> --state all --json number,state,baseRefName`. Cancella in autonomia solo i branch la cui PR verso `develop` o `<principale>` è `MERGED`; gli altri restano e si riportano con il motivo (`git.md`, «Branch», decisione D). Non chiede conferma per ogni branch. Poi:
    a. Se ci sono modifiche non committate, fermati e dillo: non cambiare branch. Esegui `git fetch --prune origin` e verifica che la PR sorgente sia `MERGED` (passo 10, sopra). Il criterio è lo stato della PR: `git merge-base --is-ancestor` non vale per gli squash. Se la PR non risulta mergiata, dillo e termina senza cancellare nulla.
    b. **Candidati alla cancellazione**, in sola lettura: branch locali già uniti in `origin/<principale>` (`git branch --merged origin/<principale>`) e branch remoti già uniti (`git branch -r --merged origin/<principale>`), più i branch locali il cui remoto è sparito (`git branch -vv`, voce `gone`). Considera solo i nomi che iniziano con `feature/`, `bugfix/`, `release/`, `hotfix/`: mai `main`, `develop`, il branch principale né il branch su cui ti trovi. Un branch fuso con squash non risulta unito per ascendenza: per questo il criterio è lo stato della PR, non l'ancestry. Un branch senza PR `MERGED` non si cancella: si elenca con il motivo.
    c. Cancella i branch verificati, uno alla volta, senza chiedere per ciascuno: locali con `git branch -d <nome>` e, se rifiuta perché lo squash non rende il branch unito per ascendenza, `-D` solo per un branch con PR `MERGED`; remoti con `git push origin --delete <nome>` (l'hook `guard-commands` lo consente solo per questi nomi). Mai `--force`. Alla fine riporta i branch cancellati e quelli rimasti, con il motivo.
    d. **Allineamento.** Con l'albero pulito: `git switch <principale>` e `git pull --ff-only origin <principale>`; poi `git switch develop` e `git pull --ff-only origin develop`. Nessun merge, nessun rebase, nessun commit su `develop`. Se un `--ff-only` fallisce, dillo senza forzare. Resta su `develop`.
    e. Controlla `git rev-list --count origin/develop..origin/<principale>`: se è maggiore di zero, `develop` non contiene più `main` dopo il merge. Segnalalo e proponi il branch `bugfix/sync-main-into-develop` con PR verso `develop` a merge commit, come al passo 4 (branch e merge come descritto al passo 4; la PR verso `develop` si apre poi con `/kit:pr-develop`, ricordando all'utente che quella PR va chiusa con merge commit e non con squash). Non eseguire altro senza il suo ok.
