# PR verso il branch principale

Rispondi in italiano. Una sola domanda per messaggio e attendi la risposta. Titolo e descrizione in inglese. Non fare mai `push --force`, non fare il merge della PR, non cancellare branch e non creare tag o rilasci: sono richieste a parte.

0. **Prerequisito: GitHub CLI installata e autenticata.** Prima di tutto, in sola lettura: `gh --version` e `gh auth status`. Se `gh` non è installata o non è autenticata, **termina subito** senza eseguire altro: di' all'utente quale dei due manca e cosa fare (installare la GitHub CLI; `gh auth login` da lanciare lui con `! gh auth login`, perché è interattivo). Questa skill non si usa senza `gh`. Non usare `gh` per altro che questa verifica e l'operazione richiesta.
1. **Branch principale e sorgente.** Il branch principale è la voce «Branch principale» del `CLAUDE.md`; se è un segnaposto o manca, usa quello di `git symbolic-ref refs/remotes/origin/HEAD`. Se non è `main`, segnalalo e chiedi con una sola domanda se usarlo così com'è o adottare `main` e `develop` (non rinominare nulla di tua iniziativa). La sorgente è l'argomento, altrimenti il branch corrente se inizia con `release/` o `hotfix/`, altrimenti `develop`. Se `develop` non esiste (sorgente `develop`), termina e chiedi come procedere.
2. **Riga nel `CLAUDE.md`.** Leggi nel `CLAUDE.md` della radice la riga «GitHub CLI (gh) installata». Se manca o dice «no» (ora che il passo 0 ha verificato `gh`), chiedi con una sola domanda di confermare che è installata e scrivi la riga `- **GitHub CLI (gh) installata:** sì (AAAA-MM-GG)` nella sezione «Eccezioni alle regole globali»: il hook `guard-commands` blocca `gh pr` senza quella riga.
3. **Stato in sola lettura.** `git status --short` (modifiche non committate: segnalale, la PR contiene solo i commit), `git log --oneline origin/<principale>..<sorgente>` per i commit che arrivano, `git diff --stat origin/<principale>...<sorgente>`. Se non ci sono commit nuovi, dillo e termina. Verifica che la sorgente sia allineata al remoto (`git rev-list --count <sorgente>..origin/<sorgente>`); se è indietro, segnalalo: l'aggiornamento è dell'utente.
4. **`main` avanti rispetto a `develop`.** Solo con sorgente `develop` o `release/*`: esegui `git rev-list --count origin/<sorgente>..origin/<principale>`. Se è maggiore di zero (dopo un hotfix, o dopo uno squash già avvenuto), una PR verso il principale andrebbe in conflitto (`add/add`) sui file già portati. Non aprire la PR. Spiega il problema e proponi, con una sola domanda, il branch locale `bugfix/sync-main-into-develop` da `develop` (se esiste già in locale o sul remoto, ad esempio di una sincronizzazione precedente, proponi il primo nome libero `bugfix/sync-main-into-develop-2`, `-3`, ... senza cancellare né riusare quello vecchio; verifica con `git branch --list` e `git ls-remote --heads origin`) con un merge commit di `main` (conflitti risolti a favore di `develop` quando il contenuto di `main` è una versione più vecchia, mostrando le versioni a confronto e il motivo, e applicando la risoluzione solo dopo l'ok). Quella PR verso `develop` va chiusa **con merge commit**, non con squash, altrimenti il conflitto torna: dopo il merge l'utente rilancia questa skill.
5. **Versione e rilascio.** Se la PR porta un rilascio, controlla in sola lettura che il file di versione e la voce `### Rilascio X.Y.Z` del `CHANGELOG.md` siano coerenti con quanto indicato nel `CLAUDE.md`; il commit di bump (`chore(release): bump version to X.Y.Z`) lo prepari solo se l'utente lo chiede. Verifica la checklist di consegna di `core.md` §0b sul lavoro che entra e riporta le voci mancanti.
6. **Titolo e descrizione.** Proponi un titolo Conventional Commits (per esempio `merge: …` o `chore(release): …`, al massimo 72 caratteri) e una descrizione con i commit che entrano raggruppati per categoria (**Aggiunto**, **Modificato**, **Corretto**, **Sicurezza**), gli impatti (migrazioni, variabili d'ambiente, breaking change) e il riferimento alle issue (`Closes #N`). Il commit di merge avrà oggetto `merge: <sintesi> (#NNN)` con un corpo che riassume la funzionalità: dillo all'utente, che fa il merge. Chiudi con `🤖 Generated with [Claude Code](https://claude.com/claude-code)` se il `CLAUDE.md` chiede l'attribuzione di Claude.
7. **Conferma.** Mostra sorgente, destinazione, titolo, descrizione e i comandi, e chiedi con una sola domanda: «Faccio push della sorgente e apro la PR?». Senza un sì non eseguire nulla.
8. **Esecuzione.** Dopo il sì: `git push -u origin <sorgente>` se la sorgente non è già sul remoto allineata (push normale, mai forzato); poi `gh pr create --base <principale> --head <sorgente> --title "<titolo>" --body-file <file temporaneo>`. Se la PR esiste già, mostra l'indirizzo e non crearne un'altra. Il hook `guard-commands` blocca `gh pr` finché la riga del passo 2 non dice «sì».
9. **Chiusura.** Mostra l'indirizzo della PR. Ricorda: merge con **merge commit**, mai squash né rebase; il lint dei commit non si esegue sulle PR verso il principale; dopo un `hotfix/*` il ritorno di `main` in `develop` è un merge commit. Merge, tag e rilascio (`gh release`) restano a cura dell'utente o a una richiesta esplicita separata. Non usare `gh` per altro (né stato, né CI, né altre PR).
