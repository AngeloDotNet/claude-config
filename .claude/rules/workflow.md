# Regole di interazione: workflow esteso

> Richiede `core.md`. Estratto da `core.md` §6, con la stessa numerazione: i riferimenti «§6.N» restano validi. Caricato nei profili standard e strutturato; nel profilo mini sta in `.claude/rules-optional/`.

## 6. Regole di interazione con l'utente (estratto)
1. **No codice legacy:** niente `NgModule`, `Startup.cs`, `*ngIf/*ngFor`, `APP_INITIALIZER`, interceptor a classe.
2. **Niente terze parti per mapping/dispatching:** non proporre MediatR né AutoMapper. L'handler/servizio ha la forma scelta dal progetto (`backend-architecture.md` §2a) e il mapping avviene tramite estensioni. La libreria di gestione errori è `OperationResults` di Marco Minerva, scelta fissa (la variante AppEngine è sospesa, vedi `backend.md` §1).
3. **Modifiche mirate:** per file esistenti mostra solo la funzione o le righe modificate, indicando il path del file e circa 3 righe di contesto. I file nuovi vanno mostrati per intero.
4. **Chiarimento architetturale:** l'architettura (Vertical Slice o Clean) si decide una volta per progetto e sta nel `CLAUDE.md` di progetto. Chiedi solo se non è specificata e il progetto è nuovo; nei moduli successivi segui la scelta già fatta.
6. **Definition of Done:** codice + test + nuove chiavi di traduzione (IT/EN) + eventuale migrazione EF. Per una nuova entità o funzionalità che attraversa più strati l'ordine di lavoro è quello di `feature-workflow.md` (solo se incluso: modulo opzionale dei progetti fullstack).
10. **Regole di progetto:** le specificità (nome soluzione, database, comandi di build) stanno nel `CLAUDE.md` del singolo progetto. Questi file restano generali.
12. **Refactoring ampi:** se la richiesta implica toccare molti file o cambiare un'architettura esistente, descrivi il piano e chiedi conferma prima di procedere.
13. **API delle librerie:** non fidarti della memoria per API che cambiano spesso (Angular, PrimeNG, `OperationResults`, FusionCache): controlla la versione installata e la sua documentazione.
17. **Qualità del codice:** il codice è leggibile e manutenibile e privilegia la semplicità. Niente astrazioni, interfacce o livelli aggiuntivi senza un motivo dichiarato (overengineering): nel dubbio si sceglie la soluzione più semplice che soddisfa il requisito. Claude segue sempre le convenzioni del linguaggio, il naming, la formattazione e lo stile del progetto.
18. **Best practice su conferma:** una best practice che introduce una scelta nuova (pattern, libreria, struttura non presente nel progetto) Claude la propone con il motivo e attende il via dell'utente, una per volta, prima di usarla. Quelle già previste da queste regole si applicano senza chiedere.
20. **Analisi non ripetuta:** La issue padre (punto 15) contiene anche le conclusioni dell'analisi già fatta (file esaminati, decisioni, esito delle verifiche), così che una sessione successiva riprenda dal piano senza rifare l'analisi da zero.
23. **Deroghe ai controlli automatici:** il plugin `kit` blocca in scrittura alcuni pattern vietati dalle regole (test saltati, Angular legacy, librerie vietate, EF InMemory, API insicure, SQL interpolato, `npm install` nel Dockerfile, TLS disattivato). Una deroga legittima si dichiara nel codice, sulla stessa riga o su quella sopra, con l'id della regola e un motivo: `kit-allow: <id> — <motivo>` (es. `// kit-allow: skip — rimandato alla CI notturna`). Senza id corretto o senza motivo il blocco resta. Ogni deroga aggiunta in una pull request è elencata dal controllo CI `kit-allow` (`_template/ci/`), con file e riga, e va approvata in review come ogni eccezione (`security.md`, «Crittografia»: soppressioni con approvazione). Gli avvisi di pratica usano gli stessi id: `scrittura-blocco`, `soppressione`, `anonimo`, `regex`, `log`. A fine sessione il plugin ricorda, senza bloccare, CHANGELOG non aggiornato, migrazione EF mancante e chiavi di traduzione IT/EN non allineate (§0b).
- **15b · Piano di sviluppo già scritto (backend, frontend o fullstack):**Piano di sviluppo già scritto (backend, frontend o fullstack):** se l'utente fornisce un piano (file o testo, scritto prima o altrove), Claude non lo ignora né lo riscrive da zero: lo **verifica** rispetto a queste regole e al `CLAUDE.md` e riporta l'esito prima di eseguire. (a) **Conflitti** (es. MediatR o AutoMapper, dipendenza a pagamento, scelta diversa da `CLAUDE.md`, commit su `main`, ordine dei passi in contrasto con `feature-workflow.md`): per ciascuno si ferma e chiede conferma, **una domanda per volta**, e non applica la parte in conflitto finché non risponde (§6.5, §6.14); la risposta che vale oltre il caso va nel `CLAUDE.md`. (b) **Mancanze** rispetto al formato del punto 15 (obiettivo, assunzioni, sub-issue, file coinvolti, test previsti, decisioni aperte) e ai passi sempre dovuti (aggiornamento di `README.md` e `CHANGELOG.md`, migrazione, chiavi di traduzione IT/EN, security review dove serve): le propone **una per volta**, con una domanda singola, e **solo dopo la risposta dell'utente** le aggiunge al piano (o le scarta), prima di passare alla successiva e prima di procedere con l'esecuzione; le voci aggiunte sono distinte in modo visibile dai punti originali (es. etichetta "aggiunto da Claude") ed elencate nel riepilogo, senza modificare né riordinare i punti dell'utente. Nessuna voce entra nel piano senza una risposta. Il risultato è registrato come issue padre con le sub-issue e si esegue con la regola dei passi con via libera qui sotto; la conversione vale anche se il piano originale è in un altro formato o file, che resta com'è.
